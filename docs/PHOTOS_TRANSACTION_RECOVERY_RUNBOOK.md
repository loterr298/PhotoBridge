# Photos 导入事务恢复验收（0.3.6/build10）

当前状态：代码和本机无 PhotoKit 的测试可运行；新二进制云编译、真机事务恢复与人工观察分别记录，不预填通过。

## 协议与停止边界

仅新协议会话可继续。不可变计划绑定收件 UUID、尝试 UUID、精确清单/USB 请求 hash、源相簿/成员、新相簿名及原授权选项。每个事务先提交意图，在 PhotoKit changes block 中保存 placeholder 标识；Apple 说明该标识在实际对象创建后保持一致。持久化失败无法撤销已排队的 PhotoKit 请求，故缺少标识、对象不可见或状态不明确一律拒绝重放。不会按名称或拍摄日期查找并猜测副本。

重新预检和继续必须检查目标相簿名、完整成员前缀/顺序、已记录对象的实际可见性及已回读修改版本；每次运行把全部已有资源重新回读到新 verification-attempts/UUID 目录，再创建剩余项。旧文件和部分回读保留。旧版失败会话没有此计划，继续拒绝；不要拿旧失败会话测试恢复。

单写入者原生文件锁只协调遵循协议的本 App。每次事务全量检查前缀；万张吞吐尚未测试。日志并非抵御任意恶意修改的签名存储，也没有突然断电的完整耐久性承诺。

## 3 张 Live Photo 真机步骤

1. Mac 用已完成且全量校验的原 3-Live 备份，通过 USB-only 上传到全新 UUID 收件目录，ready 最后提交。不覆盖旧收件或相簿。
2. 用户沿用原 Apple ID 个人签名覆盖安装，不卸载旧 App。Mac 读取新诊断/恢复记录确认实际运行源码版本。
3. 手机“恢复”选择新会话，严格模式（时间授权关闭）预检；展开中断恢复诊断，开启“首个 Photos 事务完成后停止”，开始创建。
4. 停止后 Mac 只读保存计划、意图、placeholder 和进度基准。必须有同一相簿 ID、首个资产 ID；新建数1、回读数0。确认实际新相簿仅1成员。这是受控提交后/回读前停止，不是提交中强杀。
5. 用户完全关闭 App 再打开，同一会话重新预检并继续。相簿名及授权保持原值。先重新回读首个资产，再创建其余2项；无需打开诊断开关。
6. Mac 用 tests/device_restore_audit.py USB 独立取回最终新 verificationDirectory 全6份资源，用系统 shasum 核对；最终映射首个 ID 必须等于基准。核对新建数2、复用数1、总资产3及完整顺序，重新取基准文件验证 bytes/mtime/birthtime/nlink 未变。计数来自 App 日志；实际资源字节由外部验证。
7. 用户在系统照片确认3项自定义顺序及每张 Live Photo 播放。记录原话，不用 JSON 代替人工观察。

所有源照片、备份原字节、内部 EXIF/MakerNotes/GPS、旧日志和失败会话保留。shouldMoveFile=false。此次 Live 样本不需要编辑时间例外；含 type7 的后续样本只有用户已授权且默认关闭的选项可接受新副本 adjustmentTimestamp，其余字段仍严格拒绝变化。

未验证场景须继续标 NOT_RUN：提交中进程/系统终止、磁盘满、权限撤销、iCloud 原件缺失、任意日志破坏、更多格式及规模性能。状态不明确时停止是保护结果，不是恢复通过。
